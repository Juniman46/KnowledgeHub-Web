# ナレハブ｜KnowledgeHub

<b>写真と一言でチームに相談</b>

## （１）サービス概要

<b>ナレハブ｜KnowledgeHub</b>は、一人で現場対応に迷ったスタッフが、仲間の過去の対応をスマホで探せる少人数チーム向けのWebアプリです。<br />　記録で解決できないときは、<b>写真と一言で仲間に相談</b>できます。<br />　実際に対応した人が結果を一言で残し、必要に応じてAIの「整う」で文章を整えられます。

## （２）アイデアの背景

### 約10年前、電話で問い合わせを受けていた頃

私は現在の職場で約10年前、複数の拠点から様々な問い合わせを電話で受ける業務を担当していました。日々似たような質問が繰り返され同じ説明を繰り返すうちに、<b>一度調べたことを記録に残すことで同じチームが、時間をかけずに同様の回答ができる</b>ようにと、質問の共有化を図るため、Accessで質問と回答を共有化することに挑戦しました。

しかし、日々鳴り止まない電話に対応するだけの毎日を繰り返すうちに、記録の仕組みを作る気力を次第に失い、口伝えのまま引き継ぎを行うだけとなっていました。

### 職場でExcel版を作ったきっかけ

私の職場では、業務に使えるツールに制約があり、過去の問い合わせや回答を共有するには、普段使っているExcelを活用するのが現実的でした。業務システムが切り替わったとき、現場から同じような質問が相次ぎました。問い合わせを受けるスタッフは窓口での接客も担当していたため、<b>目の前のお客様に向き合う時間を確保したい</b>と考えました。

そこで、かつて挑戦しようとした、情報共有化の仕組み作りに再び挑戦するため、RUNTEQで学んだプログラミングの知識とExcel／VBAの技術、そしてAIの力を用いて、窓口のスタッフが本来の接客業務に集中できるように、現場の社員が過去の回答を探したうえで、質問ができる情報共有化ツール、エクセル版のKnowledgeHubの開発に取り組みました。

### Web版をピラティスの現場へ

また、私は趣味で10年ほどピラティスを続けており、スタジオに通ううちにさらに学びたいと考え、ピラティスの指導方法を学び、業界でも難関と言われているBalanced Bodyのマットインストラクター資格を取得し、現在は更にマシンの資格取得に挑戦中です。

今回、KnowledgeHubのWeb版を最初に誰に使ってほしいかと考えたとき、顔が浮かんだのは、インストラクター試験の養成課程で出会った仲間や、身近なスタジオで働くインストラクターでした。

日々現場で忙しい仕事をこなすなか、レッスンに必要な器具が壊れたとき、レッスンの合間にスマホを開いて、器具の写真を撮り、一言を添える。<b>それだけで仲間に状況がいかに早く、正確に伝わるか</b>を、まず確かめたいと思っています。

Web版で大切にしたいのは、スタッフの活きた経験・知恵をそのまま残しつつ、できるだけ簡単に記録に残すことです。

例えば「壊れた器具の型番と部品の写真をメーカーの窓口に送ったら、交換部品を手配してもらえた。」ほかに詳しい説明がなくても、この一言には次の人が使える<b>経験</b>があります。

体裁を整えるために説明を書き直す手間はAIに手伝ってもらいつつ、できるだけ対応した人の言葉を残したいと考えました。これが忙しかった当時の自分が欲しかった機能です。

## （３）解決したい課題

たまにしか起きない困りごとほど、「どこから手をつければ良いんだ？」と手が止まります。私の職場では、以前対応した人がその場にいないと、どこに連絡すればよいか分からないことがありました。その人に聞くしかなかったのは、対応結果が本人の記憶にしか残っていなかったからです。電話で解決した直後には次の接客や問い合わせが待っていて、一言のメモも後回しになりました。この経験から、次の三つを課題と考えています。

1. <b>困ったその場で相談できる相手が見つからず、最初の対応に迷う。</b><br />　詳しいスタッフが誰か分かっていても、接客中ですぐには聞けないことがあります。また、設備や備品に不具合が起きたとき、購入店とメーカーのどちらに、何をどう伝えればよいか迷うこともあります。<b>仲間の過去の記録</b>に今回にも当てはまる対応があれば、返事を待たずに自分で解決できます。
2. <b>スタッフがそれぞれの方法で問題を解決しても、他の人が何を試してどうなったかが伝わりにくい。</b><br />　たとえば、あるスタッフがメーカーに依頼して備品を交換し、その結果を記録したとします。そこに別のスタッフが「前に同じ部品で困ったときは、購入店に頼んだらその日のうちに対応してもらえた」と一言添えれば、次の人はその二つの経験をもとに、<b>今回の状況に合う</b>相談先を選べます。
3. <b>目の前の業務を優先すると、「何をして、どう解決したか」を次の人のために残しにくい。</b><br />　お客様からの電話にその場で答えて解決すると、何を確認してどう答えたかが、担当者の記憶にだけ残ることがあります。私自身、後のために回答を残そうと思っても、次の問い合わせや別の業務に追われ、<b>一言のメモさえ書けない</b>ことがありました。また、自分の担当内で解決できた案件は、改めて書き残す必要を感じない人もいました。

まずは、小規模スタジオでこの流れがどの程度起きるのか、最近実際に困った一件と、そのときの調べ方を聞いて確かめます。

## （４）最初に使ってほしい人と利用場面

最初に使ってほしいのは、数人で運営するピラティススタジオで、レッスンとお客様対応を同時に担うインストラクターです。例えば、レッスン前に壊れた備品の復旧方法を確認したいのに、以前同じ対応をした同僚はその場にいない。PCの前に戻る時間はなく、手元のスマホなら確認できる、という場面です。

このアプリは業種を限定していません。接客やレッスンの合間に、<b>スマホ片手で短時間に</b>確かめたいという状況を重視しました。まずは対象とするスタジオで前回の対応をスマホ片手で確かめられるかを試し、将来は少人数で業務を分担するような、前の担当者の経験を次の人が必要とする他の職種でも役立てたいと考えています。

### モニターに協力を依頼して分かったこと

私自身のピラティス養成課程で培ったつながりを通じて、インストラクターや他業種の方を含む16人の方にモニター協力を依頼しました。試作画面を操作した方からは「過去に相談した内容も探せる？」という質問や、一問一答は見やすいものの、回答文から具体的な方法を読み取るのは難しいという感想を頂きました。

小規模スタジオを運営するインストラクターからは、紹介画像を見た段階で、スタッフが一人でお客様対応をしていて困ることが実際に多くそんな時にこんなアプリがあれば助かるとのことでした。実際の利用頻度や、対応後に記録を残し続けられるかは、これから検証を行なっていきます。

実際にスタジオ運営をしているインストラクターに試作画面を使ってもらったところ、操作方法を説明しなくても、スマホを片手に持ったまま検索から入力まで進めていました。一方で、同じ質問が重なりそうだという声もありました。

### スタジオでの試用

加えてスタジオ運営を行うオーナーにも、最初は架空の設備相談をスマホで一件試してもらいます。既存の連絡手段は使い続けながら、後日また尋ねられそうな対応から試せる形にします。実際の業務で使う前には、チーム内での閲覧範囲、入力してよい情報、AIへの送信範囲などをオーナーと調整していきます。

かつて私自身が経験した、ただ目の前の問題を解決していくだけの日々を過ごしていた頃に求めていた機能を実現させたいという想いが、このサービスには込められています。

## （６）提供したい価値

<b>　「メンバーが入れ替わっても、新しく加わった人が前任者の対応記録を使い、自分の力で次の一手を決められる。」</b>

一人で困ったスタッフが、その場にいない経験者の対応を自分の状況と照らし合わせ、次にどんな対応をするのかを決められることが第一の価値です。それによって同じ問い合わせが減れば、答える側も目の前のお客様や<b>本来の仕事に時間を使えます。</b>

チームが持つルールなど、実際に現場で働くスタッフの経験や知恵を残し、困ったときに次の一手を決められることでチームの時間を創り出そう！そんな想いを込めたサービスです。

## （７）MVPで実現すること

ナレハブでは相談から始まった一件も、自分で解決して残した一件も<b>「記録」</b>と呼びます。まず、スマホの最初の画面に並ぶ共通のカテゴリボタンを押して、記録の一覧を開きます。件数が多いときは、検索窓でさらに絞り込めます。カテゴリボタンは、急いでいてもひと目で選べる数にこだわりました。カテゴリから探すときは文字を打たずに済み、相談・返答・対応結果を残すときは短いフリック入力で足りる設計を目指します。

「設備・備品」「お客様対応」は仮称です。ボタンの名前・数・並びは、複数業種の事例を使い、投稿する人と後から探す人が同じ入口を選べるかを試して決めます。

| 現場でやりたいこと | MVPで用意するもの |
| --- | --- |
| 「前にどうした？」を調べる | ログイン後、選んだカテゴリの「チームの記録」がカードで並ぶ。相談の一言や、対応した本人が残した結果の一言を載せ、写真があればサムネイルを添える。結果がまだなら「結果の記録待ち」と示す。次にすることが分かれば、一覧で確認を終えられる。 |
| 候補を絞る・気になる一件を確かめる | 候補が多いときは、一覧の検索窓で相談文・回答・対応結果にある言葉を使って絞り込む。カードをタップすると、相談、仲間の助言、日付付きの対応結果を読める。一覧に戻ると、選んだカテゴリや検索語を引き継ぎ、開いたカードの位置から続きを見られる。 |
| 見つからなかったので仲間に聞く | 選んだカテゴリのまま短い相談文を投稿する。必要なら設備や備品の写真を1枚添える。入力欄には「分かれば、名前や場所もひとこと」と添える。同じチームのメンバーがアプリ内で短文を返せる。 |
| 実際にどうなったかを残す | 対応した本人が「やってみた結果」を一言で記録する。自力で解決したときも、カテゴリを一つ選んで対応結果から直接記録できる。別の場面でも役立つ結果を残したときは、その記録にカテゴリを追加できる。どちらの一覧からも同じ一件を開ける。 |
| 読む人のために文章を整える | 本人が「整う」を押したときだけ、入力した対応メモの本文をAIに送る。「試したこと」「分かったこと」の短い下書きと原文を見比べ、修正・採用するか、原文のまま保存する。 |
| 次の人の経験を足す | 別のメンバーが検索した記録に、自分が試した結果を日付・記録者付きで追記する。前回の記録も読める。 |

### 閲覧と共有の範囲

初回MVPでは、開発者が検証用のチームを一つ用意し、スタッフはそれぞれ自分のアカウントで参加します。先に参加したスタッフが対応結果を残した後、開発者が新しいスタッフを手動でチームに追加します。新しく加わった人が、参加前の記録を探して自分の対応結果を追記できることを確かめます。

設備や備品のトラブルは、部品の名前や状況をうまく説明できるまで待ってくれません。質問者は、その場で分かることを自分の言葉で投稿できます。

- 投稿した時点で、質問の原文と添えた写真はログインした同じチームの全員が閲覧でき、仲間はその相談に回答できます。回答も投稿した時点でチームに共有されます。
- AIの下書きは本人が確認して保存するまで他のメンバーには表示しません。対応結果を共有する判断は実際に対応した本人が担います。
- 検索結果と添付写真にも同じチームの閲覧制限を適用します。

### 架空のデモで確かめる一件

1. <b>Aが探して相談する</b><br />　スタッフAが「設備・備品」を押し、一覧の写真と一言を見比べる。候補が多いので検索窓に「フットバー」と入力する。参考になる記録が見つからず、そのカテゴリのまま部品の写真に「これ、前どこに聞いたっけ？」と一言添えて投稿する。チームのBには、Aが書いた言葉と写真がそのまま見える。
2. <b>Bが助言し、Aが対応結果を残す</b><br />　Bが「メーカーに聞いてみて」と回答する。実際に動いたAは「型番と写真を購入店に送った。交換窓口を教えてもらえた」と残す。「整う」の下書きを確認し、チームに共有する。
3. <b>後から加わったCが記録を使う</b><br />　後日、Aが対応結果を残したチームにスタッフCが加わる。Cは部品名を知らない。「設備・備品」を押し、一覧の写真からAの記録を見つける。カードにある対応結果の一言を読んで「まず、この機種の型番と購入店を確認しよう」と判断できれば、一覧だけで用が済む。<br />　経緯を確かめたいときはそのカードを開き、Bの助言とAが実際に取った対応を読み分ける。一覧に戻ると、同じカードの位置から続けて見比べられる。Cも自分の対応結果を追記できる。

この例でAIが「部品を交換した」と書いたら求めている「整う」の機能ではありません。無駄のない綺麗な文章よりも、<b>飽くまでスタッフの活きた経験の情報が重要</b>だからです。また、AがAIを使わずに保存しても、Cは同じように原文を探せるようにします。

初回は質問の写真1枚とテキストの対応結果で一巡できる範囲に絞り、フォームからデータベースに保存し、その場でチーム内検索に反映します。

### 本リリース以降の候補

オーナーが自分でスタッフを迎え入れる段階で、既存のチームへの招待機能を用意します。別のスタジオが自分たちで利用を始める段階で、チームを新規作成する機能を検討します。回答への写真添付と、古い記録の見直し通知も候補とします。

## （８）懸念点と対策

| 懸念 | MVPでの対応と確かめ方 |
| --- | --- |
| AIが助言と実績を混同する | 入力元を本人の対応メモだけに絞る。原文を保持し、下書きは本人が確認する。窓口判明・回答待ち・試したが改善しなかった例で、意味が変わる箇所を調べる。 |
| AIを使う方が手間になる | 同程度の架空事例を用意し、原文で残す場合と「整う」ボタンを使う場合で、記録時間、直した箇所、別のスタッフの読み取りやすさを比べる。通信失敗や利用上限に達したときも入力文を保持し、原文で保存できるようにする。 |
| 信頼してよい記録か判断しにくい | 回答と実施結果を分け、記録者・日付・対応内容が分かるようにする。以前の対応と条件が違うときは、元の記録を残して新しい結果を追記する。 |
| 写真や相談に業務上の機密が入る | 卒制デモは架空の内容と設備・備品の画像に限定する。AIへ写真・氏名・チームの履歴を自動添付しない。送信対象をボタンのそばで示す。未ログインの人や、ログイン済みでもチームに参加していない人が記録や添付写真を取得できないことを確認する。同じアカウントでチームに参加した後は、参加前の記録と写真を閲覧できることも確かめる。 |

## （９）今後の発展と検証

### 初回MVPで確かめること

最初の完了条件は、別のスタッフが説明を受けずにスマホで過去の一件を探し、「誰が何を試し、何が分かり、自分なら次に何をするか」を話せることです。対応した人の記録時間も観察し、AIの確認・修正に時間がかかるなら、整える量や表示の仕方を見直します。

スマホの一覧は、同じ記録を1列と2列で試します。部品名を伏せた写真を見せ、代行スタッフ役が片手で「前回はどこに何を送ったか」を正しく読み取れるか、答えのある記録を見落として同じ質問をしないかを確かめます。

### デモの後、現場で確かめること

短いデモの後は、以前対応した人が不在の日に記録が開かれたか、別の人が新しい結果を一言でも足せたかを協力者に聞きます。投稿数を増やすことより、次に同じ場面が来たとき実際に役立った一件を手掛かりに改善します。デプロイ後は、協力を得られた店舗での試用を目指します。

### 初回MVP後の検証候補

- <b>同じ検索語でチーム全体を探す</b><br />　選んだカテゴリで記録が見つからないとき、入力した検索語を保ったまま、同じチームの全カテゴリに検索範囲を広げる案です。検索語を打ち直さず、目的の記録にたどり着けるかを試します。
- <b>「整う」によるカテゴリ提案</b><br />　本人の対応メモをもとに、記録に追加できる共通カテゴリを一つ提案する案です。例えば「設備・備品」の相談で「お客様に振替を案内した」と残したときは、「お客様対応」の追加が候補になります。採用するかは本人が決めます。本文から判断できない場合は候補を出さず、選んだカテゴリで保存できます。<br />　導入するかは、後から探す人が記録を見つけやすくなるか、記録する人にどれだけ確認の手間がかかるかを試して決めます。
- <b>一件の相談に複数の写真を添える</b><br />　器具全体と不具合のある部品をそれぞれ撮り、同じ相談に添えられる案です。写真が1枚のときと比べて、仲間がどの部分に何が起きたかをつかみやすくなるか、相談する人にどれだけ手間が増えるかを確かめます。

## （１０）技術スタック案

| 用途 | 候補と選定理由 |
| --- | --- |
| Webアプリ・画面 | Ruby on Rails、ERB、Hotwireを第一候補とする。学んだフォームとデータ保存を生かし、検索や「整う」のプレビューは必要な箇所だけ更新する。スマホで見たときの写真・見出し・余白・タップしやすさはモックを基準に検証する。初回はRailsで画面まで扱い、Reactを分離して実装する負担を抑える。 |
| データと写真 | PostgreSQLで相談・回答・対応結果・チーム所属の関連を扱う。写真はActive Storageと非公開のオブジェクトストレージを候補とし、画面と画像の両方で所属を確認する。 |
| AI連携 | Railsサーバーからテキスト生成APIを呼び出す。入力文字数とデモでの呼び出し回数に上限を設け、APIキーはサーバー側で管理する。提供元・モデルは、架空メモでの意味の保持、応答時間、送信データの扱い、利用上限と費用を試して決める。 |
| 開発・公開 | ローカル開発は学習経験のあるDockerを利用する。公開先はRenderを候補とし、データの永続化と画像保存を含む費用を確認して決める。 |

技術面で最初に試すのは、スマホで撮った設備写真をチーム内だけで表示できることと、AIの応答が遅れたり失敗したりしても手元の一言が消えないことです。
